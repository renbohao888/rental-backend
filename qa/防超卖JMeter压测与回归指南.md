# 防超卖 · JMeter 高并发压测与回归验证指南

> 本项目「防超卖」的定义：**同一房源、同一入住时间段，不能被两个及以上订单同时占用**。
> 压测对象接口：`POST /api/order/create`（需登录态，租客/房东角色均可下单）。

---

## 一、压测前准备

1. 启动 MySQL 与 Redis；启动后端（`mvnw spring-boot:run` 或 `start_backend.cmd`）。
2. 准备测试数据：
   - 一个 `status=1`（已上架可预订）的房源，记录 `roomId`；
   - 准备 50~200 个租客测试账号（注册后调用 `POST /api/user/login` 拿 `token`）。
3. 将 `token` 保存为 CSV 文件供 JMeter 参数化使用，格式（无表头）：
   ```csv
   token_1
   token_2
   ...
   ```

## 二、JMeter 脚本结构

| 组件 | 配置 |
|---|---|
| 测试计划 | 名称：order-create-防超卖压测 |
| 线程组 | 线程数：`200`；Ramp-Up：`0` 秒；循环次数：`1` |
| CSV 数据文件 | 读取 tokens.csv，变量名 `token`，每个线程独立取一行 |
| HTTP 头管理器 | `Authorization: ${token}`；`Content-Type: application/json` |
| HTTP 请求 | POST `http://localhost:8080/api/order/create`<br>Body：`{"roomId":101,"checkInDate":"2026-10-01","checkOutDate":"2026-10-15"}` |
| 响应断言 | 返回体中包含 `code=200` 且 message 为成功文案时为“下单成功” |
| 监听器 | 聚合报告 / 查看结果树（结果树仅在压测时关闭，避免 IO 拖慢压测） |

> 补充说明：`Ramp-Up=0` 表示线程组启动后尽可能同时发出请求；
> 如需更贴近“瞬间并发”，可在 HTTP 请求前加 **同步定时器（Synchronizing Timer）**，组内线程数设为 `200`。

## 三、预期结果与判定口径

### 场景 A：200 并发抢同一房源同一时段（核心回归）
- 成功下单数（接口层面）：**1 单**；
- 失败请求均返回业务错误（文案为“该房源在此时间段内已被预订”或“正在被其他租客下单，请稍后重试”）；
- 执行 `qa/防超卖并发验证.sql`：重叠订单 **0 行**、成功落库订单 **1 行**；
- `redis-cli KEYS "lock:order:room:*"` 返回 **空**（无锁残留）。

### 场景 B：不同用户订同一房源、不同且不相邻时段（反例保护，防“误锁”）
- 2 个用户分别订 `10-01~10-10` 与 `10-12~10-20`；
- 期望：**2 单全部成功**，且验证脚本①查询仍为 0 行。
- 结论：锁的粒度是“房源ID”，只串行化校验动作，不误伤可正常预订的其他时段。

### 场景 C：边界日期（配合边界值用例）
- 相邻入住/退租（如 A：`10-01~10-10`，B：`10-10~10-20`）：
  按代码规则 `入住 < 对方退租 且 退租 > 对方入住`，`10-10` 当天不重叠 → 期望 2 单都成功；
- A：`10-01~10-10`，B：`10-09~10-20`（重叠 1 天）：期望 B 失败。

## 五、日志分析技巧（可写入简历“日志分析”能力点）

1. 后端日志搜索下单失败原因并归类：
   ```bash
   # Windows PowerShell
   Select-String -Path backend.log -Pattern "已被预订|手速太快|已下架" | Measure-Object
   ```
2. 用时间戳对比“请求进入 -> 落库”耗时，观察锁等待对响应时间的影响；
3. MyBatis-Plus 已开启 SQL 日志（`StdOutImpl`），可定位重叠校验 SQL 是否走了索引
   （排查思路：`EXPLAIN SELECT ... FROM room_order WHERE room_id=? ...`）。
